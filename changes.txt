1.13 2026/07/28
---------------
- The constellation a body stands in is now translatable.
  $almanac.<body>.constellation still renders the Latin name -- the value
  is the same string it has always been, so templates that compare it and
  loopdata fields that publish it are untouched -- but it now carries the
  other views of the same answer as attributes: .abbr the IAU
  abbreviation, .label the report's translated display name, .name the
  Latin name again.  Translate in the report's [Almanac]
  [[Constellations]] section, keyed by IAU abbreviation ("Psc = Fische");
  an untranslated constellation's .label falls back to Latin.  Works for
  every body and named star, follows each report's own language, needs no
  PyEphem, and the attribute chains work as loopdata fields
  (almanac.mars.constellation.label renders in the language of loopdata's
  target report).  $almanac.<body>.constellation_abbr remains as a legacy
  alias for .constellation.abbr.  The Sky page's planet chips ("in Leo")
  now render the .label, and the German lang file carries all 88
  constellations (Beta with the rest of de.conf; alternatives a reviewer
  may weigh are noted in the file); en.conf ships the Latin set as the
  key reference for translators.

1.12 2026/07/27
---------------
- FIX: on stations running a non-English OS locale, the analemma panel's
  month labels (Jan, Mar, Jun, Sep, Nov) silently vanished -- the months
  to label were picked by comparing strftime('%b') output against the
  English abbreviations.  Months are now picked by number, and the
  labels render in the station's own locale, as the panel's dates
  always have.
- NEW tag $almanac.<body>.label: the body's display name, translated by
  the skin.  Add the tag name to the skin's [Almanac] section (the same
  section that holds moon_phases) in a lang file or skin.conf -- for
  example "moon = Mond" -- and $almanac.moon.label renders Mond;
  untranslated bodies fall back to the English name, so a partial list
  is fine.  Works for every body and named star, follows each report's
  own language, and (like constellation) needs no PyEphem.  This opens
  the 1.12 internationalization work.
- The Sky page is now translatable, entirely through WeeWX's own
  mechanisms.  Every string the page renders -- captions, panel labels,
  tooltips, chips, table headers, the footer -- is a gettext-style
  [Texts] key: the English string IS the key, and a report falls back
  to English one string at a time, so a partial translation is fine and
  never blanks a panel.  Body names on the panels follow the [Almanac]
  section (the same source as the new .label tag), compass cardinals
  the report's [Units] [[Ordinates]] directions, and the header's
  hemisphere letters [Labels] hemispheres -- the core-standard sources,
  no invented keys.  The skin ships lang/en.conf, the reference
  dictionary: a test now fails if a rendered string is missing from it,
  or if it carries a string nothing renders, so the dictionary tracks
  the page exactly.  Set the language per report with lang = <code> in
  weewx.conf ([StdReport] [[SkyfieldReport]]); month and date names
  already follow the station's OS locale.  Skins embedding the panels
  get all of this through their own report's lang/[Texts] sections.
- German ships with the skin (Beta): lang/de.conf is a complete
  translation of the dictionary (a test keeps it complete, so new
  strings cannot ship untranslated).  Set lang = de in the
  [[SkyfieldReport]] section of weewx.conf.  Beta means the words,
  not the machinery: the translation awaits native-speaker review,
  and a clumsy phrase is the worst it can do -- corrections are
  welcome, as are further languages; a lang file is a self-contained,
  no-code contribution.

1.11 2026/07/27
---------------
- The Sun's Path panel now marks times on the moon's dashed curve:
  moonrise and moonset get a tick and the time at the horizon crossings,
  the transit gets a tick and time at the apex, and the curve's two ends
  -- the moon's positions at 00:00 and 24:00 -- get dots labeled 00 and
  24 when they clear the plot floor.  Times honor the skin's TimeFormats;
  each mark carries a hover tooltip, the endpoint dots' explaining the
  open curve (below).  Labels dodge the sun's hour labels, and the
  transit label yields to a nearby endpoint label rather than crowd it.
  Skins embedding sunpath_svg with hand-copied CSS rules: the labels use
  a NEW class, moonlab -- copy its rule from sky.css or the labels
  render at the 16px SVG default.
- Root cause of the above, and now also explained in the caption: a user
  spotted a gap at the top of the moon's arc near full moon and read it
  as a bug.  The panel plots midnight to midnight, but a lunar day runs
  about 50 minutes longer than a calendar day, so the moon's 24-hour
  track is an open curve -- the break sits wherever midnight catches the
  moon, and around full moon (moon transiting near midnight) that is
  right at the apex, above the plot floor where it shows.  The plot was
  correct all along: the moon genuinely does not cross those azimuths
  that day.  The 00/24 endpoint dots now make the break read as the day
  boundary it is.  (README and manual updated to match.)

1.10 2026/07/25
---------------
- FIX: on Skyfield 1.53 (the version Debian trixie packages) the almanac
  failed to start: "init: Could not find earth in ephermis file ...:
  'InMemorySpiceKernel' object has no attribute 'codes'.  The Skyfield
  almanac will not run."  Reports then fell through to the built-in
  PyEphem/weeutil almanac -- planets right, stars and Proxima gone, easy
  to misread as a star-catalog problem.  The in-memory ephemeris kernel
  (1.6, the SIGBUS guard) reproduced SpiceKernel.__init__'s assignments,
  and that set changes between Skyfield releases: 1.53's __init__ also
  sets codes and _vector_functions, 1.54's sets neither.  The kernel now
  reuses SpiceKernel.__init__ verbatim, swapping the SPK factory it
  consults for one that serves the already-read bytes, so it tracks any
  Skyfield release's initialization exactly (verified against 1.53 and
  1.54).  Skyfield 1.47 remains the minimum.
- The Sky page footer now tells the truth about what computed the page,
  instead of printing the full Skyfield/DE421/Hipparcos credit as static
  text no matter what.  The full credit appears only when the registered
  Skyfield almanac and its star catalog are actually live; when stars were
  requested but the catalog failed to load, the footer says "star catalog
  unavailable -- see the weewxd log"; with stars = false it says "star
  catalog disabled"; and when weewx-skyfield never registered at all (the
  page then renders off the built-in almanac's fall-through) it credits
  the built-in almanac and points at the log.  Field case: a user
  diagnosing missing stars quoted the old footer's Hipparcos credit as
  evidence the catalog had loaded -- it hadn't; the footer is now a
  place that failure shows.  (The ESA acknowledgment is required exactly
  when Hipparcos data is displayed, so it moves with the star credit.)
- Housekeeping: WXSKYFIELD_VERSION and SKIN_VERSION now match install.py
  again -- both had been left at 1.9 through the 1.9.1 release (install.py
  alone was bumped; it is one version scheme, not three).  A test now pins
  the three sites in lockstep.
1.9.1 2026/07/23
----------------
- Sample skin: the Sky page's card titles (<p class="eyebrow">) are now
  real <h2> headings, satisfying the current Nu Html Checker's rule that
  every <section> carry a heading (h1 -> h2 cards, no level skips).  The

1.9 2026/07/18
--------------
- New eclipse tags, with no PyEphem counterpart: next_/previous_
  lunar_eclipse and next_/previous_solar_eclipse give the time of maximum
  of the nearest eclipse VISIBLE from the station (the eclipsed body above
  the horizon at maximum), each with a _type companion --
  penumbral/partial/total for lunar; for solar, the type as seen from the
  station (partial/annular/total), so inside the penumbra of a total
  eclipse the reported -- and observed -- type is partial.  Lunar
  eclipses come from Skyfield's eclipselib; solar eclipses are found
  natively, testing each new moon for a topocentric sun/moon disc
  overlap at the station.  The combined next_eclipse/previous_eclipse
  (with _kind and _type companions) picks the sooner (later) of the two
  kinds, so skins need no selection logic of their own.
- Every body, stars included, reports its constellation:
  $almanac.saturn.constellation ("Pisces") and .constellation_abbr
  ("Psc"), judged from the observer's topocentric place against the IAU
  boundaries (the boundary map ships inside the Skyfield library;
  nothing is downloaded).
- The Sky page: the countdown row gains the next eclipse visible from
  the station (lunar or solar, whichever is sooner, with its locally
  seen type and the year on its date), and each planet chip names the
  constellation the planet stands in.
- The README now explains why the bundled ephemeris is DE421 rather than
  the newer DE440s: the accuracy difference is invisible at almanac
  precision (refraction at the horizon dwarfs it), while DE440s would
  double the size of the release zip and the installed extension (new
  section, "Why the DE421 ephemeris (and not DE440)?").

1.8 2026/07/12
--------------
- weewx could fail to shut down if the SIGTERM landed during the Skyfield
  almanac's startup ephemeris/star-catalog load: weewxd stops by raising
  Terminate inside whatever the main thread is running, and Sky.__init__'s
  log-and-continue handlers swallowed it.  They now hand Terminate back.
- The Sky page's single-column layout (below 1160 px, e.g. phones and most
  iPads) no longer shrinks every section to its content width: the sky
  dome, timelines and table now fill the viewport as intended.  (The grid
  rule's align-items:start carried over into the flex-column fallback;
  the fallback now sets align-items:stretch.)

1.7 2026/07/11
--------------
- Three new panels on The Sky page, each embeddable in your own skin like
  the rest (README: "Using the Sky panels in your own skin"):
  * The Solar Year (daylength_svg) -- sunrise, sunset and solar noon for
    every week of the year over the civil/nautical/astronomical twilight
    bands, today marked in brass.  Local clock time, so the DST steps in
    spring and fall are real; polar day and polar night shade correctly.
    The costliest panel on the page (several hundred rise/set searches),
    but its samples anchor to fixed weekly instants, so the 1.4 result
    cache reuses them across report cycles -- the full price is paid once
    after startup, not every cycle.
  * The Lunar Month (lunation_svg) -- the current lunation, new moon to
    new moon, as thirty phase discs with the principal phases dated and
    today's disc ringed in brass.
  * The Sun's Path (sunpath_svg) -- today's altitude/azimuth arc with a
    dot every hour, the moon's path dashed beside it, twilight-depth
    bands below the horizon, on a fixed whole-compass azimuth axis so
    the arc's seasonal swing reads at a glance.
- The README now documents embedding the Sky panels in your own skin: a
  new section, "Using the Sky panels in your own skin", covers the
  skin.conf search-list registration, the sky.css classes the markup
  relies on, and every panel -- the three new ones included -- with its
  template snippet and a screenshot.  All screenshots moved from the
  repository root into screenshots/, and the Sky page's computation-cost
  note now reflects the result cache.

1.6 2026/07/08
--------------
- The engine now reads the DE421 ephemeris fully into memory instead of
  letting jplephem memory-map the file.  Rewriting the .bsp in place under
  a running weewxd -- exactly what "weectl extension install" over a live
  WeeWX does -- could kill the process with SIGBUS if a computation caught
  the sub-second copy window; the running engine is now immune to the file
  changing (or vanishing) underneath it.  Costs about 16 MB of resident
  memory.
- The Hipparcos star data licence is now documented: ESA distributes the
  Hipparcos and Tycho Catalogues under CC BY-NC 3.0 IGO, and the README,
  wxskyfield_stars.dat and the Sky page footer now carry the required
  "Credit: ESA" acknowledgment.  The wxskyfield_stars.dat header also no
  longer calls itself celestial_stars.dat (a leftover from the celestial
  3.x extraction).

1.5 Release 2026/07/08
----------------------
- Traditional astronomy colors on both chart plates.  The Sky page charts
  (and any skin embedding them) now draw the bodies the way star atlases
  do: yellow sun, silver moon, gray Mercury, pearly Venus, blue Earth.
  Mars, Jupiter, Saturn, Uranus, Neptune and Pluto were traditional
  already and are unchanged.  Two values bend tradition for legibility,
  the same compromise printed atlases make: Mercury keeps the gray FAMILY
  at two weights (dark on the light plate, light on night), and Neptune
  stays a readable mid-blue on night.  Pale bodies (sun, moon, venus) gain
  a thin per-body ring on the light plate -- on the dome and orrery dots,
  the ribbon bars (1px stroke) and the chip/table dots (inset box-shadow)
  -- so they hold their edge on paper; the night plate needs no rings and
  its markup stays as before apart from the new fills.
  This is a VISUAL change to default output: no API, tag, skin or
  configuration change, but pages will render with the new colors on the
  first report cycle after upgrading.  Skins attached to the old look can
  pass palette='classic-night' or palette='classic-light' -- the pre-1.5
  palettes, preserved verbatim.

1.4 Release 2026/07/08
----------------------
- Result cache: expensive almanac computations are now cached at the
  computation layer, transparently (no configuration, no new tags).
  Day-window searches -- rise/set/transit, the effective-horizon body
  radius, and the next_*/previous_* events -- are reused across report
  cycles (a day's moonrise is computed once, not once per mention per
  page per cycle; a "next full moon" found once is served until it
  happens).  Instantaneous positions (alt/az, ra/dec, magnitudes, moon
  phase) are keyed on the exact timestamp: repeats within a cycle
  collapse, including desktop/smartphone twin pages and almanac_time
  loops anchored to fixed instants; a position at a new timestamp is
  always freshly computed.  Only raw floats are cached, never
  ValueHelpers, so skins with different formatters cannot leak into each
  other.  One deliberate tolerance: rise/set cache keys quantize the
  effective horizon to 0.002 degrees (refraction scaled by the almanac's
  live temperature/pressure drifts a few thousandths of a degree per
  cycle; without quantization nothing would ever be reused).  Worth well
  under a second of event time (worst measured 0.64 s over a 15-hour
  replay of real sensor data), below the refraction model's own
  uncertainty and small enough that displayed minutes agree with a fresh
  computation except when the true time sits within that fraction of a
  second of a minute boundary.
  Pools are bounded and cleared wholesale on overflow; correctness never
  depends on an entry being present.  The first cycle after a WeeWX
  restart or after local midnight runs at full uncached cost while the
  day's entries repopulate.  Measured on the eight-page
  paloaltoweather.com site (~3,200 tag evaluations per cycle, Raspberry
  Pi 5): template generation 17.7 s -> ~4.6 s per warm cycle.
- Sky page resilience: every $sky_page method (moon_svg, dome_svg,
  ribbons_svg, orrery_svg, analemma_svg, chips_html, table_html,
  countdown_html, header_sub, sun_is_up) now catches its own failures,
  logs the error, and renders that panel blank -- an unexpected error
  costs one panel, not the whole Sky page for that report cycle (defense
  in depth after the skyfield edge case guarded in 1.3).  Template-author
  errors are unaffected: an unknown palette name still raises the error
  listing the valid names.

1.3 Release 2026/07/06
----------------------
- Harden rise/set/transit event conversion against a rare skyfield
  numerical edge: find_risings/find_settings can emit a wildly wrong event
  time (near Julian day zero -- "Python's datetime does not support
  negative years like the year -4713") when a body barely grazes the
  horizon.  Converting it crashed template generation for that report
  cycle (seen once in production).  Event times are now filtered to the
  search window before conversion (a time outside the window is by
  definition not that day's event), in the new stamps_within helper used
  by both find_rise_set and find_transit.  Regression test included.
- Housekeeping: SKIN_VERSION in skins/Skyfield/skin.conf now tracks the
  extension version (it had been left at 1.0 through 1.1 and 1.2; the skin
  files themselves were unchanged in those releases).

1.2 Release 2026/07/06
----------------------
- Chart label placement fixes, prompted by the paloaltoweather.com celestial
  pages.  One backward-compatible API addition (dome_svg's label_scale,
  below); everything else is output markup only:
  * analemma_svg: month labels and the "today" label now sit radially outward
    from the figure's centroid, so they clear the curve at the lobes (Jun at
    the top, Dec/Jan at the bottom) and the axis labels; a month label that
    would land on the today label is skipped.
  * orrery_svg: body labels flip to the inside using an estimated text width
    (a fixed threshold clipped Saturn at the right rim), are clamped
    vertically, and de-overlap when neighbors share a rim (Saturn/Neptune
    near 0 degrees for years to come).  The 0-degree ray label is anchored
    inside the viewBox so it survives skins that enlarge .gridlab.
  * dome_svg: new optional label_scale argument grows every dome label
    (stars, bodies, cardinals, ring degrees) by that factor, with font sizes
    emitted inline so the collision layout matches the rendered size --
    useful for skins whose pages are scaled down (fixed-canvas smartphone
    layouts).  Default 1.0 keeps today's sizes.
  * dome_svg: labels are placed after all marks with collision handling --
    body labels (Sun/Moon/planets) nudge vertically until they clear each
    other; star labels are dropped on a collision (their dots keep the hover
    title).  The cardinal letters and the 30/60-degree ring labels are
    seeded into the collision layout, so body labels dodge them too.
    Planets bunched along the ecliptic no longer print over each other,
    and labels near the rim flip inward instead of clipping.

1.1 Release 2026/07/06
----------------------
- Every $sky_page render method (moon_svg, dome_svg, ribbons_svg,
  orrery_svg, analemma_svg, chips_html, table_html, countdown_html,
  header_sub) takes an optional palette argument selecting the colors
  baked into its markup: 'night' (the default -- the shipped Sky page's

  listing the valid names.

1.0 Release 2026/07/05
----------------------
Initial release.  The almanac engine is extracted from weewx-celestial 3.0
(which embeds the same engine alongside its loop-packet fields); this
extension carries the report almanac alone.

- Replace WeeWX's built-in almanac (PyEphem or weeutil) for report
  generation.  Requires WeeWX 5.2 or later (the first release with
  extensible almanacs) and Skyfield 1.47 or later (the first release
  with find_risings/find_settings; on an older Skyfield the extension
  logs an error and leaves the built-in almanac in place).  Report tags
  such as $almanac.sunrise,
  $almanac.moon.transit, $almanac(horizon=-6).sun(use_center=1).rise and
  $almanac.next_full_moon are computed with Skyfield and JPL's DE421
  ephemeris, which is installed with the extension (no downloads at
  runtime).  PyEphem is not required.
- Everything WeeWX's built-in almanac computes is computed natively,
  including physical attributes ($almanac.venus.mag via Skyfield's
  Mallama/Hilton photometric models, phase, size/radius/radius_size,
  circumpolar/neverup, parallactic_angle), the moon's libration and
  selenographic colongitude (Meeus ch. 53), Jupiter's central meridian
  longitudes (IAU rotation elements) and Saturn's ring tilt (Meeus ch. 45).
  With PyEphem installed, anything this extension does not compute (e.g.,
  moon.subsolar_lat) falls through to the built-in almanac, as do almanac
  times outside the span of the bundled DE421 ephemeris (mid-1899 through
  2053); without PyEphem, all tags of the standard skins (and much more)
  work with Skyfield alone.
- The Sky page: a bundled one-page showcase skin (Skyfield), installed
  automatically and generated at <HTML_ROOT>/skyfield/index.html each
  report cycle.  A sky dome of the sun, moon (at true phase), planets and bright
  IAU-named stars above the station's horizon; rise/set ribbons over USNO
  twilight bands; an orrery of heliocentric longitudes; a weekly analemma;
  event countdowns; Jupiter CML, Saturn ring tilt and a full almanac
  table.  Self-contained HTML/inline SVG (no JavaScript libraries, web
  fonts or runtime downloads); location comes from weewx.conf.  Disable or
  retime it in [StdReport] [[SkyfieldReport]].
- Named star support (e.g., $almanac.rigel.rise, $almanac.sirius.mag), on
  by default (set stars = false in the Skyfield section of weewx.conf to
  turn it off).  Every official proper name of the IAU Catalog of Star
  Names (the Working Group on Star Names' IAU-CSN list) that has a
  Hipparcos number is supported, plus PyEphem's names as aliases -- 420
  names in all, covering 412 stars.  Star data comes from
  wxskyfield_stars.dat, an excerpt of the Hipparcos Catalogue (ESA SP-1200,
  1997; CDS VizieR I/239) installed with the extension.  Any other
  Hipparcos star can be addressed by catalog number ($almanac.hip_57939);
  install a full hip_main.dat in the user directory to serve all 118,218
  Hipparcos stars.  Unlike PyEphem, earth_distance and sun_distance work
  for stars with a measured parallax, in astronomical units.
- Where PyEphem and standard astronomical conventions differ, the almanac
  follows the standard definitions (see "Differences from PyEphem" in the
  README): custom horizons are geometric (no refraction), matching the
  USNO twilight definitions (an explicit horizon=0 cannot be
  distinguished from the default and gets the default
  refraction-and-radius treatment; use pressure=0 with use_center=1 for
  the geometric crossing of the true horizon); circumpolar/neverup use
  the same effective horizon as rise/set, so they always agree; rise/set honor the almanac's
  pressure/temperature (refraction is scaled from the standard 34
  arcminutes, and WeeWX's documented pressure=0 idiom turns it off);
  hlongitude/hlatitude are true heliocentric coordinates for every body
  including the moon, and for the sun they report Earth's heliocentric
  coordinates per the XEphem convention; $almanac.separation() takes
  (longitude, latitude) tuples and returns radians per the WeeWX 5.2
  almanac API, additionally accepts this almanac's own body binders
  ($almanac.separation($almanac.mars, $almanac.venus)), and calls made
  with PyEphem Body arguments are passed through to PyEphem when
  installed.
- The bundled files are prefixed wxskyfield_ (wxskyfield_de421.bsp,
  wxskyfield_stars.dat) so that no other extension can claim them (and
  remove them on its uninstall).
- A malformed record in the star catalog disables only that star, not the
  entire catalog; a missing catalog degrades to per-tag errors, never a
  crash of report generation.
- A pytest test suite (tests/test_almanac.py), including permanent parity
  audits against the built-in almanac.  Run with:
  /path/to/weewx-venv/bin/python -m pytest tests
