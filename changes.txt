weewx-skyfield change history
-----------------------------

2.1.3 (2026/08/13)
------------------
- Fixed: on WeeWX 5.2, every tag that carries a display name --
  $almanac.<body>.label, .constellation.label and
  $almanac.next_meteor_shower.label -- reported an error instead of a
  name, and the Sky page, which uses them for its body names and its
  constellation figure labels, failed with them.  Those names come from
  the report's [Almanac] section, which WeeWX only hands to an almanac
  from 5.3 on.  They now fall back to the English and Latin names, which
  is what 5.3 gives them anyway when a report translates nothing.  The
  5.2 floor stands.  Found by way of bellrichm's report against
  weewx-loopdata (its issue #15).
- Translating body, constellation and meteor shower names is now
  documented as needing WeeWX 5.3; the manual and the README had called
  the Sky page "fully translatable" without qualification.  Computed
  values, moon_phases, and the [Texts], [Units] and [Labels]
  translations are unaffected on 5.2.
- A countdown chip for something happening today now says when.  "today"
  alone is the least a chip ever tells you, at the moment interest in it
  is highest -- it does not say whether the event is still ahead -- and
  the clock time is the only fact the chip is not already carrying, since
  the line above it is the date.  The new-moon chip on the morning of an
  eclipse now reads "today at 11:14".  Suggested by Jacques Terrettaz,
  following his report of the day-count bug fixed in 2.1.2 (issue #6).
  The string is a single translatable phrase with a {time} placeholder,
  so a translation chooses its own word order, and it ships in all nine
  bundled languages.

2.1.2 (2026/08/12)
------------------
- Fixed: a countdown chip disagreed with its own date.  An event later
  today read "in 1 day" beside today's date -- Jacques Terrettaz saw it
  on the morning of the 2026-08-12 partial solar eclipse, and on that
  day's new moon (issue #6).  The day count was computed by rounding
  elapsed seconds up, which calls anything still ahead of the clock a
  whole day; rounding down instead would only move the disagreement to
  the other side of midnight, calling an event at 00:30 tomorrow
  "today".  The count is now the difference between the two local
  calendar dates, which is how a reader counts days off the date the
  chip is already showing, and cannot contradict it.  It is also right
  across a daylight-saving change, where 23 and 25 elapsed hours are
  both still one day.  Jacques diagnosed this and proposed the fix.
  The satellite panel's pass rows, which carry a date too, get the same
  count: a pass 30 hours out is tomorrow, not in two days.  Below a day
  those rows keep their finer "in 2 h" / "in 20 min" resolution.
- The download's size is no longer stated as a total.  The README and
  the Installation page each named a figure for the whole zip, and it
  went stale every release that changed a screenshot -- it was wrong
  three times in a month.  Both pages now name only the two bundled
  files that make the download large, the DE421 ephemeris and the
  complete Hipparcos star catalog, whose sizes are fixed, and leave
  the total and the screenshots' share unnumbered.  The two pages had
  also drifted apart from each other on the ephemeris, one counting in
  binary megabytes and the other in decimal; they now agree, in the
  decimal megabytes the releases page reports.  A test reads the
  bundled files' real sizes and fails if a documented number stops
  matching, if the sentence carrying it is reworded away, or if a
  total download size creeps back into the prose.

2.1.1 (2026/08/12)
------------------
- Fixed: on a narrow screen the Sky page opened with the Equation of
  Time panel instead of the dome.  Below the 1159px breakpoint the
  page's two columns dissolve into one and the panels are resequenced
  by CSS `order`; the Equation of Time panel, new in 2.1, was never
  given a number, so it took the default of 0 and sorted ahead of
  everything else.  It now sits where the wide layout puts it, after
  Day Length and before the lunation panel, and a test asserts every
  panel carries an order -- the next new panel cannot repeat this.
  Reported by Paul R Anderson, with the diagnosis and the fix
  (issue #5).
- The user manual is rebuilt.  It goes from seven pages to seventeen,
  on a real sidebar with full-text search, and gains the pages it was
  missing: Configuration (every option in one place, gathered from the
  three pages that each held part of it), Tag index (all 125 tags this
  extension serves, A to Z, with each one's type, units and the release
  it arrived in), Values, units and types (degrees vs radians, the
  ValueHelper twins, and the .raw trap that silently rescales a
  duration), Recipes (paste-able template snippets), Accuracy and
  conventions, Upgrading, Live-updating pages, Performance, Glossary
  and Troubleshooting.  Nothing was dropped along the way: the result
  cache, the differences from PyEphem and the DE421 rationale moved to
  pages of their own, and Known Skyfield Issues is now a section of
  Troubleshooting, with its old URL redirecting there.
  Every page carries a link to the project on GitHub, and the theme's
  own advertisement is gone from the footer.
- The Sky page's credit line now names the sources of the data it
  draws: CelesTrak for satellite orbital elements (when satellites are
  configured), the Minor Planet Center for comet elements (when comets
  are), and the International Meteor Organization for the shower list.
  Both new strings are translated in all nine bundled languages.
- The README is a front door rather than a second copy of the manual.
  It keeps the description, the highlights, installation, credits and
  licensing, and links to the manual for the detail it used to
  duplicate -- one place for each fact instead of two that drift apart.
  The description now introduces the Sky page -- what it is, where it
  is published and that it redraws every report cycle -- instead of
  dropping the screenshot in unexplained, as does the manual's home
  page, and a row of buttons at the top goes to the manual, the
  current release's zip and the issue tracker.  The ready-to-paste
  block of famous comets moved to the manual's Configuration page.
- Skins that embed the Sky panels: the panels page now documents
  $sky_page.footer_html(), which it had never covered.  That is the
  credit line -- and it carries the ESA acknowledgment that showing
  Hipparcos data requires -- so an embedding page should include it.
- The Translations page now says who translated what.  A per-language
  table gives each of the eight bundled translations its file and its
  status, crediting Gert Andersen for the Danish, Christian (peters77)
  for the German review and Jacques Terrettaz for the French -- named
  until now only in the README -- and saying plainly which files are
  still awaiting a native speaker.  Each review is dated to the release
  it covered (1.14, 1.15, 1.17), because the strings added since --
  satellites in 2.0, comets and meteor showers in 2.1 -- are complete
  and tested but not yet read by a native speaker; the page says so
  rather than implying the whole file was reviewed.  The page also
  stops calling the count nine: eight translations ship, beside
  lang/en.conf, which is the reference dictionary rather than a
  translation.
- The test suite keeps the manual and the code in lockstep.
  Twenty-four audits now fail when the two disagree: a served tag
  missing from the tag index, a broken internal link or anchor between
  manual pages, a [Skyfield] option or a Sky page default that does not
  match what the code actually reads, a documented option nothing reads,
  an undocumented $sky_page panel, a translation dictionary that has
  drifted from lang/en.conf, an installer default the docs quote
  wrongly, a documented constant -- the refresh intervals, the element
  age limit, the visible-pass altitude -- that no longer matches the
  code, a manual URL written in a form GitHub Pages does not serve, a
  page missing its title or its link line, a broken README button, a
  language table that has drifted from the shipped lang files, and
  a recipe whose tag chain no longer evaluates.  Documentation drift is
  a test failure now, rather than something a user finds.

2.1 (2026/08/10)
-----------------
- ACTION REQUIRED (isolated networks only): 2.1 adds this extension's
  second runtime download.  With comets configured -- the installer
  configures Halley and Hale-Bopp -- weewxd fetches the Minor Planet
  Center's comet elements (one ~160 KB CometEls.txt covering every
  comet with a current orbit) from minorplanetcenter.net at install
  time, at any startup that finds the file missing or stale, and then
  about every two days, on a worker thread that never blocks reports.
  Set comet_downloads = false in the [Skyfield] section of weewx.conf
  to fetch nothing, ever; [[Comets]] still works in that mode if you
  maintain the element file yourself -- the README's Comets section
  has the air-gapped story.  Stations that do nothing get working
  comet tags out of the box.
- The almanac serves comets.  [Skyfield] [[Comets]] maps tag names to
  Minor Planet Center designations -- the installer writes the two
  comets everybody knows, halley = 1P and hale_bopp = C/1995 O1 (the
  1997 great comet, now ~49 AU out and receding; dec -85, so it never
  rises from northern stations and costs a northern dome nothing) --
  and each entry serves the full planet-style surface: rise/set/
  transit and the whole next_/previous_ family, alt/az and every ra/dec
  flavor, distance/distance_from_sun (and the raw AU floats),
  elongation, visible, illumination, constellation, and mag.  The value
  is the designation as the MPC file prints it (12P, C/2023 A3,
  fragments named explicitly as C/1947 X1-B), matched after case and
  whitespace normalization only.  There is deliberately no pass
  machinery -- a comet rises and sets daily, like a planet -- and comet
  tags never fall through to PyEphem, which has no comets.  Elements
  are the MPC's CometEls.txt, ONE ~160 KB file for every comet with a
  current orbit, cached as wxskyfield_comets.txt beside the satellite
  TLEs: fetched at install, at any startup that finds it missing or
  stale, then about every two days on a worker thread -- written
  atomically, the old file kept on any failure, backoff on retry --
  and comet_downloads = false fetches nothing, ever (the satellites'
  air-gapped story, one file to maintain by hand).  A comet the MPC
  drops from the file serves honest N/A tags with a once-per-crossing
  warning, never an error; elements_epoch and elements_age stay live
  as diagnostics, and there is no age cutoff -- two-body elements
  degrade gracefully over months, so positions are documented as
  where-do-I-look accuracy, with the engine's per-tag caches
  invalidated the moment the element file refreshes.  mag is the MPC
  g/k total magnitude with a documented caveat: comets are notorious
  for deviating from it.  On the Sky page's dome a risen configured
  comet is a labeled diamond with a small tail pointing anti-sunward
  (as comet tails do; radially outward on the sun-centered orrery) --
  solid brass when plausibly naked-eye (magnitude 6.0 or brighter), a
  hollow ring when fainter, the satellite-in-shadow convention -- with
  the magnitude in the tooltip,
  comet_names() joining satellite_names() as a public contract,
  data-bright joining data-sunlit as an embedding hook, and the footer
  crediting the Minor Planet Center.  The orrery plots configured
  comets too -- a diamond at the comet's CURRENT sun distance on the
  panel's log scale, at its heliocentric longitude, marker only (an
  eccentric orbit does not draw as a circle), true distance in the
  tooltip -- the panel that shows a news-cycle comet falling sunward
  across report cycles, horizon or no horizon.  Comets ride the rest
  of the page's roster panels as well: a row in the almanac table, a
  brass-dotted chip in the rail (whose eyebrow then reads "Sun,
  Planets & Comets"), and a brass bar on the rise & set ribbons --
  each honestly absent when the comet has no elements, and magnitude
  shown as a dash when the MPC row carries no g/k parameters.  And
  one tag of the comet's own: $almanac.halley.perihelion, the time of
  perihelion passage straight from the MPC elements (it can honestly
  lie in the past -- Hale-Bopp's says 1997); the header's countdown
  row shows it only when it lies ahead within a year, the news-cycle
  chip, while Halley's 2061 date stays quiet until its time comes.
  Strings translated in all nine bundled languages.
- The almanac knows the dozen major annual meteor showers (the IMO
  working list, Quadrantids through Ursids).  Each peak is anchored to
  the SUN'S ECLIPTIC LONGITUDE, the way meteor astronomy states it --
  the Perseids peak when the sun reaches 140.0 degrees, whatever the
  calendar says -- so every year's peak instant is computed from the
  ephemeris, never looked up, the table needs no annual maintenance,
  and the solver reproduces skyfield's own equinox instant to the
  second.  $almanac.next_meteor_shower always serves the shower next
  ahead, as plain attributes: .name (stable English data), .label
  (translated via [Almanac] [[MeteorShowers]] -- a closed named set
  like the constellations, tables in all nine languages), .peak,
  .zhr, .radiant_ra/_dec with the live refracted .radiant_alt/_az,
  and .parent, the body whose debris it is (the Perseids are comet
  109P/Swift-Tuttle's trail; the Eta Aquariids and Orionids are both
  Halley's).  $almanac.active_meteor_showers lists every shower whose
  activity window contains the almanac's time, each with its own
  apparition's peak, honestly kept even when already past.  The Sky
  page's countdown row always carries the next shower with the moon's
  peak-night illumination as the interference judgment ("Perseids --
  Aug 12 -- in 4 days -- moon 0%": the 2026 peak lands on a new moon,
  a dark-sky year), and while a shower is active the dome marks its
  radiant with a rayed glyph -- meteors stream outward from that
  point -- ZHR and peak date in the tooltip.
- New unit-aware distance tags for every body, stars included:
  $almanac.<body>.distance (from Earth -- mirroring the satellites,
  whose .distance is likewise the distance from the observer) and
  .distance_from_sun are ValueHelper twins of the raw AU floats
  earth_distance/sun_distance -- "1.8588 AU" by default in every unit
  system, converting on ask ($almanac.moon.distance.km,
  $almanac.mars.distance.mile).  The astronomical_unit unit registers
  with WeeWX in its own group, group_distance_astronomical, so [Units]
  [[Groups]]/[[StringFormats]]/[[Labels]] entries can restyle the whole
  family (default format %.4f, default label " AU").  A star whose
  catalog record has no measured parallax has no known distance: its
  twins report N/A rather than a fictitious number.
- $almanac.<body>.illumination is the ValueHelper twin of the raw
  percent-illuminated float phase (and of the moon's moon_fullness
  alias): the same value in group_percent, honoring the report's
  percent formatting.  mag keeps no twin, deliberately: a magnitude
  is a unitless number, there is nothing to convert or label.
- The moon serves its apsides: $almanac.moon.next_perigee,
  .previous_perigee, .next_apogee and .previous_apogee are the times
  of the moon's closest and farthest approach -- the supermoon
  machinery.  The extremum is searched on the geometric
  center-to-center distance, the definition the published apsis
  tables (Meeus; Espenak) use, reproducing them to the minute; the
  results are cached like the almanac's other event tags, and near
  the edges of the ephemeris span the tags report an honest N/A.
  Moon only: no other served body orbits the observer, so any other
  body raises a clean per-tag error.
- Solar time and the equation of time: $almanac.solar_time is the
  local apparent solar time -- what a sundial reads -- as an angle in
  decimal degrees like sidereal_time (180 is solar noon),
  $almanac.solar_angle its unit-aware twin, and
  $almanac.equation_of_time a signed duration ValueHelper: apparent
  minus mean solar time, positive when the sundial runs ahead of the
  clock -- the USNO sign convention, noted in "Differences from
  PyEphem" since published sources disagree on the sign.  Values agree
  with Meeus within a few seconds across the year.
- The Sky page charts the equation of time: a new Equation of Time
  panel beside the Solar Year chart -- sundial minus clock for every
  week of the year, sampled at the analemma's own instants (local
  standard noon), the classic double-humped curve on a fixed
  +/-18-minute frame, the brass point labeled with today's value --
  its own standard-noon evaluation, since snapping to the weekly grid
  would mislabel the seconds-precision value by up to ~90 seconds near
  the December solstice.  The analemma's brass marker gets the same
  fix: today's own noon sun on the figure-eight, where it sat up to
  3.5 days along the locus at the nearest weekly sample before.
  Served by the new $sky_page.eot_svg for embedding skins;
  translated in all nine bundled languages.
- Earth's own apsides are tags: $almanac.next_perihelion and
  $almanac.next_aphelion (with previous_ twins), top-level like
  next_solstice -- the closest and farthest approach to the sun, early
  January and early July, the same geometric-extremum machinery as the
  moon's apsides and matching the published instants within a minute.
  Built on celestial's ask, for its countdown row's fifth windowed
  guest.
- The supermoon rule is a tag: $almanac.next_supermoon is the instant
  of the next full moon falling within a day of perigee, searched
  forward full moon by full moon -- the engine's single copy of the
  definition, which the Sky page's callout reads instead of
  re-deriving, and the one field a live page's supermoon countdown
  needs.
- The Sky page's lunation panel gains an apsis footer: the quiet
  next-perigee/next-apogee line, topped by a brass Supermoon callout
  whenever the next full moon falls within a day of perigee.  Like
  the satellite pass cards, the callout is anticipation -- it appears
  ahead of the event and leaves with it.  Served by the new
  $sky_page.moon_apsides_html for embedding skins; translated in all
  nine bundled languages.

2.0 (2026/08/08)
-----------------
- ACTION REQUIRED (isolated networks only): 2.0 is this extension's
  first release that downloads anything at runtime.  With satellites
  configured -- the installer configures the ISS and Tiangong -- weewxd
  fetches each satellite's orbital elements (a ~200-byte TLE) from
  CelesTrak at install time, at any startup that finds them missing or
  stale -- a satellite added to weewx.conf is live seconds after the
  restart -- and then about every three hours, on a worker thread that
  never blocks reports.  Set satellite_downloads =
  false in the [Skyfield] section of weewx.conf to fetch nothing,
  ever; [[Satellites]] still works in that mode if you maintain the
  element files yourself -- the README's Satellites section has the
  air-gapped story.  Stations that do nothing get working satellite
  tags and pass predictions out of the box.
- The almanac tracks earth satellites.  [Skyfield] [[Satellites]] maps
  tag names to NORAD catalog numbers (iss = 25544; the one list drives
  both the tags and the fetch list), and each entry serves the usual
  position surface -- $almanac.iss.alt/.az/.ra/.dec, their unit-aware
  siblings, .distance (slant range), .sunlit -- plus the pass family,
  first of its kind in WeeWX: $almanac.iss.next_pass and
  .next_visible_pass, each with .rise/.culmination/.set,
  .max_altitude, .rise_azimuth/.culmination_azimuth/.set_azimuth
  (compass ValueHelpers, .ordinal_compass renders "WSW"), .duration
  and .visible.  Visible means sunlit while your sky is dark (sun
  below -6 degrees) at some moment of the pass, peaking at least 10
  degrees up; a pass is a geometric horizon crossing and
  $almanac(horizon=10).iss.next_pass reuses the existing horizon
  argument; an in-progress pass IS next_pass until it sets.  For a
  satellite, .rise/.transit/.set are the next occurrence from the
  almanac's time, transit meaning culmination.  sat_<norad> is an
  alternate spelling for a listed satellite, mirroring hip_<number>.
  Elements whose epoch is more than seven days older than the almanac
  time are never used: every tag honestly reads "N/A" rather than
  reporting confidently wrong pass times (one log warning at the
  crossing, one at recovery), and the always-live diagnostics
  .elements_epoch and .elements_age say why.  On a failed fetch the
  old file is kept and the retry backs off; element files live one per
  satellite, wxskyfield_sat_<norad>.tle, in a wxskyfield directory
  under SQLITE_ROOT, and survive restarts (weectl extension uninstall
  does not remove them).  Deliberately absent: an apparent-magnitude
  tag (brightness models are hand-wavy; sunlit and max_altitude are
  served honestly instead).
- Live-updating pages want the companion releases shipped alongside
  2.0: weewx-loopdata 6.9 or later -- earlier versions could cache a
  temporarily-unavailable satellite field's "N/A" until the day rolled
  over instead of recovering with the elements -- and weewx-celestial
  8.0 or later, built against this release's satellite and dome
  contracts.  The docs' live-updating sections now name both floors
  (loopdata was previously "5.0 or later"), and both sections show what
  the pairing buys: an animated capture of this extension's dome on the
  weewx-celestial page (screenshots/live_dome_tiangong.gif) -- Tiangong's
  July 15 zenith pass, marker inverting to a hollow ring mid-crossing as
  it enters Earth's shadow, replayed through the live page on the
  orbital elements Space-Track archived that day.
- The Sky page shows the anticipation half of the satellites: a
  Satellites panel -- one card per configured satellite with its next
  visible pass, countdown-chip date rolling into "overhead now",
  then "appears WSW / peaks 45 degrees SSW / disappears NE / 6 min" --
  and a Next Visible Pass chart, the soonest upcoming visible pass drawn on
  its own sky: the whole sky as it will stand at the pass's
  culmination, the pass arced across it dashed and time-labeled, rise
  and set times at the endpoints, the satellite's own dot at the peak,
  under a dated head line ("ISS / Sun Jun 22 / 03:11 -> 03:21 / peak
  19 deg").  One chart, one epoch: a future track on the "now" dome
  would cross stars it will never cross and read its undated times as
  tonight's, so the pass gets the per-pass chart convention
  (Heavens-Above's) and the main dome stays strictly the current sky,
  drawing a satellite only as a position dot when one is genuinely
  overhead at generation time.  The pass chart's star field is cut
  off at magnitude 3.5 -- the stars a half-dark pass-watching sky
  actually shows -- and the panel disappears entirely when no
  satellite has a visible pass in the coming week.  The rows are
  honest: no visible pass in the coming week says so, and no usable
  orbital elements says that instead, pointing at the weewxd log.
  Stations with no [[Satellites]] configured render the page exactly
  as before, no satellite section at all.  Embedding skins pick the
  chart up as $sky_page.pass_chart_html (empty string when passless;
  SVG ids distinct from the dome's) and, if copying individual CSS
  rules, need the new .satlab rule (the satellite name label) plus
  .passhead/.passname/.passwhen (the chart's dated head line); the
  panel strings are new [Texts] keys, translated in all nine shipped
  languages, and the satellite display names come from [Almanac]
  (iss = ISS), where the shipped lang files also carry tiangong and
  hst.
- The dome's satellite dot tells sunlit from shadowed: a sunlit
  satellite is the solid brass dot, and one inside Earth's shadow
  inverts to a hollow ring -- the open-symbol convention for
  present-but-not-shining -- with its tooltip ending "in shadow"
  (translated in all nine shipped languages).  On the Next Visible Pass
  chart the peak dot can be that hollow ring: a pass is visible when
  any of it is sunlit in a dark sky, and a morning pass often exits
  Earth's shadow just after culminating, so the chart honestly shows
  the satellite flaring into view mid-sky.  The marker group carries
  data-sunlit="1"/"0" alongside data-body -- part of the consumer
  contract below -- so weewx-celestial's live dome can flip the dot
  live as a satellite crosses the shadow line.
- Every dome mark an embedding skin might reposition carries a
  machine-readable hook: the sun's, moon's and each planet's marks are
  wrapped in <g class="dome-body" data-body="mars">, their name labels
  carry the same data-body attribute, and a satellite's position dot
  gets its tag name the same way; the pass arc's group,
  <g class="dome-track" data-body="iss">, lives on the Next Visible Pass
  chart, whose marks carry the same hooks as the dome's.  The tooltip
  text is translated and was never a usable selector.  And the
  configured satellite list is enumerable: $sky_page.satellite_names()
  returns the tag names in config order (empty when none are
  configured or the almanac is not registered).  Both are consumer
  contracts -- weewx-celestial's live dome (celestial 8.0) repositions
  marks between report cycles through the hooks and builds its
  satellite roster and live layer from the list -- so they are stable.
- The page's tooltips now answer taps.  Every mark's tooltip is a
  native SVG <title>, which browsers show only on hover -- and a touch
  screen has no hover, so on an iPad every tooltip was simply dead.  A
  small dependency-free script, sky.js, installed and copied beside
  sky.css, now shows the same text in a floating chip when a mark is
  tapped: the tap snaps to the nearest mark within 24 CSS px (the
  dome's fainter stars are 1-3 px dots, blunter than any finger), a
  tap on empty sky, a scroll or Escape dismisses it, and mouse users
  keep the native hover tooltips unchanged -- a click now also pins
  the chip.  The two captions that said "Hover any mark" now say
  "Hover or tap", reworded in all nine shipped languages.  Embedding
  skins get the same fix by copying sky.js and sky.css's new .skytip
  rule and loading the script with <script src="sky.js" defer> -- the
  panels' markup is unchanged.
- The complete Hipparcos catalog now ships with the extension, as
  wxskyfield_stars.dat.gz -- all 118,218 stars, replacing the ~400
  star excerpt.  Every $almanac.hip_<number> tag works out of the box
  (here, and on celestial and loopdata almanac fields), and the Sky
  page's dome is a full sky map for everyone.  If you had downloaded
  hip_main.dat into WeeWX's user directory per the old instructions,
  that copy is now redundant: the extension no longer reads it, and it
  can be deleted.  The release download grows to about 32 MB.
- With the full catalog always present, the dome's defaults change:
  star_mag_limit 2.6 -> 5.0 (roughly 800 stars) and star_label_mag
  1.1 -> 2.5.  The report options remain the escape hatch -- the old
  values restore the pre-2.0 sparse look.
- The [Skyfield] stars option is removed: stars are simply always
  available.  A leftover stars = ... line is ignored with a log
  warning that says so; nothing else changes.
- Complete Italian, Norwegian and Swedish translations ship with the
  skin (Beta, awaiting their native-speaker reviews): lang/it.conf,
  lang/no.conf (Bokmål; no is WeeWX's own code for Norwegian) and
  lang/sv.conf translate the page prose, every panel string including
  the new satellite strings, the body names, moon phases, compass
  points (Swedish spells east O in its compass winds but Ö in
  coordinates -- the file carries both correctly) and all 88
  constellation names, each set as on that language's Wikipedia list
  of the 88 constellations.  Select one with lang = it, no, or sv in
  the [[SkyfieldReport]] section of weewx.conf.  Tests keep all three
  complete the same way they keep the German, French, Danish, Dutch
  and Spanish.
- Docs: the Known Skyfield Issues section in the README and page
  in the user manual now say that Skyfield merged pull request #1140 --
  the fix for the rare benign RuntimeWarning from almanac.py line 339
  (skyfield issue #1114) -- on August 4, 2026, closing the issue, and

1.4 Release 2026/07/08
----------------------
- Result cache: expensive almanac computations are now cached at the
  computation layer, transparently (no configuration, no new tags).
  Day-window searches -- rise/set/transit, the effective-horizon body
  radius, and the next_*/previous_* events -- are reused across report
  cycles (a day's moonrise is computed once, not once per mention per
  page per cycle; a "next full moon" found once is served until it
  happens).  Instantaneous positions (alt/az, ra/dec, magnitudes, moon
  phase) are keyed on the exact timestamp: repeats within a cycle
  collapse, including desktop/smartphone twin pages and almanac_time
  loops anchored to fixed instants; a position at a new timestamp is
  always freshly computed.  Only raw floats are cached, never
  ValueHelpers, so skins with different formatters cannot leak into each
  other.  One deliberate tolerance: rise/set cache keys quantize the
  effective horizon to 0.002 degrees (refraction scaled by the almanac's
  live temperature/pressure drifts a few thousandths of a degree per
  cycle; without quantization nothing would ever be reused).  Worth well
  under a second of event time (worst measured 0.64 s over a 15-hour
  replay of real sensor data), below the refraction model's own
  uncertainty and small enough that displayed minutes agree with a fresh
  computation except when the true time sits within that fraction of a
  second of a minute boundary.
  Pools are bounded and cleared wholesale on overflow; correctness never
  depends on an entry being present.  The first cycle after a WeeWX
  restart or after local midnight runs at full uncached cost while the
  day's entries repopulate.  Measured on the eight-page
  paloaltoweather.com site (~3,200 tag evaluations per cycle, Raspberry
  Pi 5): template generation 17.7 s -> ~4.6 s per warm cycle.
- Sky page resilience: every $sky_page method (moon_svg, dome_svg,
  ribbons_svg, orrery_svg, analemma_svg, chips_html, table_html,
  countdown_html, header_sub, sun_is_up) now catches its own failures,
  logs the error, and renders that panel blank -- an unexpected error
  costs one panel, not the whole Sky page for that report cycle (defense
  in depth after the skyfield edge case guarded in 1.3).  Template-author
  errors are unaffected: an unknown palette name still raises the error
  listing the valid names.

1.2 Release 2026/07/06
----------------------
- Chart label placement fixes, prompted by the paloaltoweather.com celestial
  pages.  One backward-compatible API addition (dome_svg's label_scale,
  below); everything else is output markup only:
  * analemma_svg: month labels and the "today" label now sit radially outward
    from the figure's centroid, so they clear the curve at the lobes (Jun at
    the top, Dec/Jan at the bottom) and the axis labels; a month label that
    would land on the today label is skipped.
  * orrery_svg: body labels flip to the inside using an estimated text width
    (a fixed threshold clipped Saturn at the right rim), are clamped
    vertically, and de-overlap when neighbors share a rim (Saturn/Neptune
    near 0 degrees for years to come).  The 0-degree ray label is anchored
    inside the viewBox so it survives skins that enlarge .gridlab.
  * dome_svg: new optional label_scale argument grows every dome label
    (stars, bodies, cardinals, ring degrees) by that factor, with font sizes
    emitted inline so the collision layout matches the rendered size --
    useful for skins whose pages are scaled down (fixed-canvas smartphone
    layouts).  Default 1.0 keeps today's sizes.
  * dome_svg: labels are placed after all marks with collision handling --
    body labels (Sun/Moon/planets) nudge vertically until they clear each
    other; star labels are dropped on a collision (their dots keep the hover
    title).  The cardinal letters and the 30/60-degree ring labels are
    seeded into the collision layout, so body labels dodge them too.
    Planets bunched along the ecliptic no longer print over each other,
    and labels near the rim flip inward instead of clipping.

1.0 Release 2026/07/05
----------------------
Initial release.  The almanac engine is extracted from weewx-celestial 3.0
(which embeds the same engine alongside its loop-packet fields); this
extension carries the report almanac alone.

- Replace WeeWX's built-in almanac (PyEphem or weeutil) for report
  generation.  Requires WeeWX 5.2 or later (the first release with
  extensible almanacs) and Skyfield 1.47 or later (the first release
  with find_risings/find_settings; on an older Skyfield the extension
  logs an error and leaves the built-in almanac in place).  Report tags
  such as $almanac.sunrise,
  $almanac.moon.transit, $almanac(horizon=-6).sun(use_center=1).rise and
  $almanac.next_full_moon are computed with Skyfield and JPL's DE421
  ephemeris, which is installed with the extension (no downloads at
  runtime).  PyEphem is not required.
- Everything WeeWX's built-in almanac computes is computed natively,
  including physical attributes ($almanac.venus.mag via Skyfield's
  Mallama/Hilton photometric models, phase, size/radius/radius_size,
  circumpolar/neverup, parallactic_angle), the moon's libration and
  selenographic colongitude (Meeus ch. 53), Jupiter's central meridian
  longitudes (IAU rotation elements) and Saturn's ring tilt (Meeus ch. 45).
  With PyEphem installed, anything this extension does not compute (e.g.,
  moon.subsolar_lat) falls through to the built-in almanac, as do almanac
  times outside the span of the bundled DE421 ephemeris (mid-1899 through
  2053); without PyEphem, all tags of the standard skins (and much more)
  work with Skyfield alone.
- The Sky page: a bundled one-page showcase skin (Skyfield), installed
  automatically and generated at <HTML_ROOT>/skyfield/index.html each
  report cycle.  A sky dome of the sun, moon (at true phase), planets and bright
  IAU-named stars above the station's horizon; rise/set ribbons over USNO
  twilight bands; an orrery of heliocentric longitudes; a weekly analemma;
  event countdowns; Jupiter CML, Saturn ring tilt and a full almanac
  table.  Self-contained HTML/inline SVG (no JavaScript libraries, web
  fonts or runtime downloads); location comes from weewx.conf.  Disable or
  retime it in [StdReport] [[SkyfieldReport]].
- Named star support (e.g., $almanac.rigel.rise, $almanac.sirius.mag), on
  by default (set stars = false in the Skyfield section of weewx.conf to
  turn it off).  Every official proper name of the IAU Catalog of Star
  Names (the Working Group on Star Names' IAU-CSN list) that has a
  Hipparcos number is supported, plus PyEphem's names as aliases -- 420
  names in all, covering 412 stars.  Star data comes from
  wxskyfield_stars.dat, an excerpt of the Hipparcos Catalogue (ESA SP-1200,
  1997; CDS VizieR I/239) installed with the extension.  Any other
  Hipparcos star can be addressed by catalog number ($almanac.hip_57939);
  install a full hip_main.dat in the user directory to serve all 118,218
  Hipparcos stars.  Unlike PyEphem, earth_distance and sun_distance work
  for stars with a measured parallax, in astronomical units.
- Where PyEphem and standard astronomical conventions differ, the almanac
  follows the standard definitions (see "Differences from PyEphem" in the
  README): custom horizons are geometric (no refraction), matching the
  USNO twilight definitions (an explicit horizon=0 cannot be
  distinguished from the default and gets the default
  refraction-and-radius treatment; use pressure=0 with use_center=1 for
  the geometric crossing of the true horizon); circumpolar/neverup use
  the same effective horizon as rise/set, so they always agree; rise/set honor the almanac's
  pressure/temperature (refraction is scaled from the standard 34
  arcminutes, and WeeWX's documented pressure=0 idiom turns it off);
  hlongitude/hlatitude are true heliocentric coordinates for every body
  including the moon, and for the sun they report Earth's heliocentric
  coordinates per the XEphem convention; $almanac.separation() takes
  (longitude, latitude) tuples and returns radians per the WeeWX 5.2
  almanac API, additionally accepts this almanac's own body binders
  ($almanac.separation($almanac.mars, $almanac.venus)), and calls made
  with PyEphem Body arguments are passed through to PyEphem when
  installed.
- The bundled files are prefixed wxskyfield_ (wxskyfield_de421.bsp,
  wxskyfield_stars.dat) so that no other extension can claim them (and
  remove them on its uninstall).
- A malformed record in the star catalog disables only that star, not the
  entire catalog; a missing catalog degrades to per-tag errors, never a
  crash of report generation.
- A pytest test suite (tests/test_almanac.py), including permanent parity
  audits against the built-in almanac.  Run with:
  /path/to/weewx-venv/bin/python -m pytest tests
